What You're Missing
You have citation counts but not citation edges. Your Turso DB knows "paper X has 47 citations" but NOT "paper X cites papers Y, Z, W." The edges are the critical piece — that's the training signal.

The Plan (3 stages)
Stage 1: Build the Citation Edge Graph
You need a table of (citing_paper, cited_paper) pairs where both are arXiv IDs in your 1.6M corpus.

Best option: Semantic Scholar API (batch endpoint)

Why this over the other datasets:

unarXive (saier/unarXive_citrec) — uses OpenAlex IDs as labels, not arXiv IDs. You'd need an extra join step through OpenAlex to resolve them. Also only 44% of references are linked. Messy.
Science Data Lake (J0nasW/science-datalake) — 20GB of OpenAlex citation edges, but again OpenAlex IDs, not arXiv IDs. Requires DOI-based mapping.
Semantic Scholar API — you query with arXiv:2303.14957 and get back references with externalIds.ArXiv directly. No ID translation needed. And you already used S2 for your citation counts.
The concrete steps:

1. Export all 1.6M arxiv_ids from your Qdrant/Turso corpus
2. Hit S2 batch endpoint: POST /graph/v1/paper/batch
   - Send 500 IDs per request
   - Fields: references.externalIds
   - Rate: 1000 req/sec with free API key
   - 1.6M papers ÷ 500 per batch = 3,200 requests
   - Total time: ~5-10 minutes
3. For each paper, extract outgoing references where the cited paper
   also has an arXiv ID AND is in your 1.6M corpus
4. Store as: citations.parquet → (citing_arxiv_id, cited_arxiv_id)
Expected yield: ~20-40M citation edges within your corpus (based on typical arXiv citation density of ~25 refs/paper, ~50% in-corpus hit rate).

Where to run this: A simple Python script. Kaggle notebook, Claude Code, or your local machine — it's just HTTP requests, no GPU needed. Takes ~30 minutes including rate limit pauses.

Stage 2: Generate Training Triples
This is where you turn citation edges into LightGBM training data. The idea: each paper in your corpus pretends to be a "user", and its reference list is what that "user" would save.

For each "query paper" P (sample ~100K from your 1.6M):

  1. DIRECT CITATIONS (label = 2)
     R = {papers P cites that are in your Qdrant corpus}
     These are strong positives — the author explicitly chose them
     
  2. CO-CITATIONS (label = 1)  
     For each paper r in R:
       Get r's own references → papers that share references with P
     These are weak positives — topically related but not directly chosen
     
  3. RETRIEVAL CANDIDATES (label = 0 by default)
     Use P's BGE-M3 embedding → Qdrant ANN search → top 50 results
     Any retrieved paper NOT in R and NOT co-cited → label = 0
     Any retrieved paper IN R → label = 2 (override)
     Any retrieved paper co-cited → label = 1 (override)

  4. COMPUTE FEATURES for each (P, candidate) pair:
     - qdrant_cosine_score (from ANN search)
     - citation_count of candidate (from Turso)
     - paper_age_days difference
     - category_match (same primary arXiv category?)
     - shared_author_count
     - co_citation_count (how many papers cite both P and candidate?)
     ... (~30 features total)

  5. OUTPUT ROW:
     (query_id=P, candidate_id, label, feature_1, feature_2, ..., feature_30)
Volume: 100K queries × 50 candidates = 5M training rows. That's plenty for LightGBM.

Where to run this: This needs Qdrant access (ANN searches). Run on Kaggle with your Qdrant API key, or use Claude Code / your machine. The Qdrant searches are the bottleneck — at ~15ms each, 100K queries ≈ 25 minutes.
