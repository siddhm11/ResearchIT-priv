Now the clustering fix. My reasoning: the gap-based threshold over-splits at small N because gap-detection is noise-sensitive when there are few merges. The fix is two-layered:

Layer 1 — soft cap on K based on N. Average cluster size should be ≥4 papers, so K_max = max(1, ceil(n/4)). For n=5 this caps at 2; for n=10 caps at 3; for n=28+ saturates at 7.

Layer 2 — singleton merge. Any cluster of size 1 after Layer 1 gets merged into the nearest non-singleton cluster. Exception: if ALL clusters are singletons (rare, would mean a user with truly distinct interests at extremely low N), we leave them — collapsing would erase real signal.

This combo fixes the S4 case (K=4 from 5 same-domain papers → K=1 or 2) without crippling the legitimate multi-interest case (S5 with 10 mixed papers should still get K=2-3).

That backfired badly. The optimization MOVED the work, not eliminated it. With with_vectors=True, Qdrant Cloud now does the same disk read inside the search response — and the free tier is somehow even slower at it. Stage 7 ballooned from ~2s to ~36s on average. Total Tier 1: was 19s, now 45s.

Real architectural finding: Qdrant Cloud free tier can't return vectors fast — they're on disk, not in HNSW RAM. The cost is fundamental, not in our pipeline. Combining the two calls into one didn't help; it just made the single combined call slow.

Reverting and pivoting to cache. The right strategy: keep the separate retrieve call (it's at least bounded), but add an in-process LRU vector cache so repeat papers across requests are free. Same papers appear in many users' candidates — Zipf will work for us.

Final result — the latency mystery solved
Why is it still ~1s and not faster
The profiler answers the question definitively. There are three irreducible costs:

1. Qdrant Cloud free-tier disk-read tax (~600–1000ms cold per call).
Vectors live on disk, not in HNSW RAM. Every client.retrieve() for fresh vectors triggers disk I/O. We don't control this. The fix isn't speed — it's avoiding the call. Hence the LRU vector cache: pay once per arxiv_id, free forever after.

2. Per-cluster ANN search (~600–700ms warm).
K parallel query_points calls. Even warm-cached on Qdrant's side, each round-trip is ~200–300ms minimum (network + HNSW search + payload). With K=3 in parallel, the slowest one sets the floor.

3. Title-boost Turso fetch on cold candidates (~600–1000ms cold).
LIKE-scan against 1.6M rows. First request for a given query pays it. Cached after.

Everything else combined (clustering, rerank, MMR, SQLite, etc.) is <100ms.

The honest tradeoff
The cold-cache 21s first-request hit isn't fixed and may not be fixable from our side. Three options if it ever matters:

Pre-warm at startup. Read top-N most-popular arxiv_ids from Turso, call get_paper_vectors on them. Server takes ~30s to start, then every user gets warm cache. Cost: longer cold deploy.
Persistent vector cache (SQLite blob). Cache survives restarts. Storage: ~4KB × 25K = 100MB on disk. Cost: complexity.
Pay Qdrant for a warm tier. $$$. Free-tier is the bottleneck.
For pre-launch + small user base, the in-process cache is enough. After 5–10 users have hit recs, the working set warms up and everyone's fast.
